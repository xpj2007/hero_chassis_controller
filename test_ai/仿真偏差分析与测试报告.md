## 2. 代码与数据流审查

### 2.1 控制链路（`src/hero_chassis_controller.cpp:68-123`）

```
/cmd_vel ──► doCmdVelCallback()                     // 只存最后一条，没有超时
              │
update(time, period) @1 kHz（仿真时间）：
  1. target = getTargetVelocity(cmd, mode)          // mode1: lookupTransform(base,odom,Time(0),0) 旋转
  2. w_raw = 四个关节 getVelocity()
  3. w_filt = lowPassFilter(w_raw, fc)              // 一阶低通，状态不清零
  4. v_body = forwardKinematics(w_filt)
  5. applied = limitRate(target, applied, 1.5 m/s², 2.0 rad/s², period)
  6. rest = staticOffsetIntegralClear(applied, w_filt)
       rest = (|applied.vx|+|vy|+|wz| < 1e-6) && (Σ|w_filt| < 0.2)
  7. if (!rest) odometry_.updatePose(v_body, period)   // ★ 里程计被“静止”门控
  8. broadcastTransform(pose, time)  @1 kHz          // odom→base_link，z=0
  9. publishOdometry(pose, v_body, time) @1 kHz
 10. if (rest) { 四轮 setCommand(0); wheel_pid_.reset()（每周期）; return; }
 11. w_target = inverseKinematics(applied)
 12. 四路 PID：error = w_target - w_filt；输出 clamp ±5 Nm；setCommand
```

关键点：

- **odom 用的是“滤波后的轮速”**，不是原始轮速；滤波时间常数 `τ=1/(2π·150)=1.06 ms`，在 1 kHz 下 `α=0.485`，几乎没有滤波，但仍有 1~2 个周期的相位滞后。
- **odom 被 `rest` 门控**：只要 `Σabs(ω)<0.2` 且目标为 0，位姿就完全不更新；但 `/odom` 仍以 1 kHz 发布“冻结的位姿 + 瞬时轮速 twist”，两者在静止时自相矛盾。
- **PID 也在 `rest` 时被跳过**；`pid_stamp` 因此停止推进，可用来判定闩锁（实测静止稳态时 `age≈40 s`）。
- **没有 cmd_vel 超时**：`chassis_velocity_cmd_` 只在下一条消息到来时改变，最后一条指令会一直保持。
- **`lookupTransform(..., ros::Time(0), ros::Duration(0.0))`**：零超时、取“最新”变换；第一次 update 时 `base_link` 还没发布，直接抛异常并 `ROS_WARN`（日志实测 t=0.002 s 一条），此时 **`return cmd` 把世界系指令当本体系**。
- **发布频率**：`/odom`、`/tf`、4 个 `PidState` 都是 1 kHz；`/tf` 同时被自己的 `TransformListener` 订阅（1 kHz 自环）。

### 2.2 运动学、坐标与符号（已用实测校验）

URDF（`rm_description_for_task/urdf/hero/chassis.urdf.xacro`）：

- `wheel_radius=0.07625 m`；四轮中心 `x=±0.2, y=±0.2`（即 `wheel_track/2`、`wheel_base/2` 都是 0.2）；关节轴 `0 1 0`（+y 向左）；`reflect` 依次为 `lf=+1, rf=-1, lb=-1, rb=+1`（对角镜像，标准麦克纳姆）。
- 几何 `k_geom=(0.2+0.2)=0.4`；配置用标定值 `k_effective=0.389792`。
- 符号实测（`main` 阶跃段）：`vx>0` 四轮同号；`vy>0` 为 `lf-,lb+,rf+,rb-`；`wz>0` 为 `lf-,lb-,rf+,rb+`。与代码 `hero_chassis_kinematics.cpp:12-26` 完全一致，**没有轮序/符号错误**。

正/逆运动学（`hero_chassis_kinematics.cpp`）：

```
vx = r/4 (ωlf+ωlb+ωrf+ωrb)
vy = r/4 (-ωlf+ωlb+ωrf-ωrb)
wz = r/(4k) (-ωlf-ωlb+ωrf+ωrb)
ω_target = 1/r [vx-vy-k·wz, vx+vy-k·wz, vx+vy+k·wz, vx-vy+k·wz]
```

> `k` 同时出现在正、逆运动学里。改 `k` 会同时改变“轮速→里程计 yaw”和“指令 yaw→轮速”，两者自洽，但**不能修正“物理 yaw/轮速”关系随工况变化**（见 3.3）。

### 2.3 `staticOffsetIntegralClear`（`hero_chassis_controller.cpp:204-216`）

```cpp
if (target_sum < 1e-6 && wheel_sum < zero_speed_threshold) {
    if (!rest_latched_) { wheel_pid_.reset(); rest_latched_ = true; }
} else rest_latched_ = false;
```

- 单采样、无迟滞、无去抖。静止时轮速在门限附近抖动 → 闩锁反复进出；进入时 `Pid::reset()`（清零 p/i/d 并置 `valid_p_error_last_`），`update()` 的 rest 分支又每周期 reset（没有 compute，本身无害）；真正的问题是 **闩锁一退出就立刻用 P 项响应轮速噪声**，形成 0.1 Nm 量级的间歇刹车。
- 静止判据用的是 **滤波后轮速的和**，不是“车体是否真的静止”；落地整定、滑移、滚子蠕动都可能让 `Σabs(ω)` 在 0.02~0.2 间波动。
- 门控同时作用于 odom，于是 **“轮子在转但门控判定静止”** 的真实慢速运动被丢掉（见 3.1 的 `ungated-wheel` 对比）。

### 2.4 mode 1 的世界系变换（`hero_chassis_controller.cpp:228-256`）

```cpp
odom_in_base = tf_buffer_.lookupTransform(base_frame, odom_frame, ros::Time(0), ros::Duration(0.0));
tf2::doTransform(v_in, v_out, odom_in_base);   // 只用旋转
```

- 数学上正确：`v_base = R(-yaw_odom)·v_world`。
- 但 `yaw_odom` 来自 **本控制器自己发布的轮式 odom TF**。只要 odom 航向有误差，世界系指令就会被转错方向，而车真的往错方向走，odom 又继续按错的航向积分 → **正反馈**。3.4 的实测方向误差与 odom 航向误差逐项吻合。
- 在 1 kHz 实时线程里查 TF：涉及字符串、mutex、监听线程和网络；`Time(0)` 取“最新”，不是本次 `time` 的插值；监听滞后时 `lookupTransform` 可能返回几毫秒前的 yaw。第一周期必然失败。
- 失败时 `return cmd`，即 **静默降级为 mode 0**，没有任何状态标志。

### 2.5 TF / odom 发布（`hero_chassis_controller.cpp:132-185`）

- TF 与 odom 使用 **同一个 `odom_pose`、同一个 `time`**，因此二者数值必然一致（第 3.5 节的 bag 校验也证明了这一点）。用户看到的“TF 偏差”本质就是 **odom 偏差**。
- `odom_trans.transform.translation.z = 0.0`，`publishOdometry` 的 `position.z=0`；而 Gazebo 真实 `base_link` 的 z 稳态 **0.1447 m**（main；pidzero bag 0.1472；随接触状态 ±2 mm）。`base_link` 不是地面点，正确的 2D 做法应是 `odom→base_footprint`（z=0）+ `base_footprint→base_link`（z=0.1448），或者直接发布 `z=0.1448`。现在 RViz 里机器人会“沉”到地面以下约 14.5 cm。
- 位姿/速度协方差没有填（默认全 0），对后续 EKF/导航不友好。
- 1 kHz 的 `/odom`、`/tf` 和 4 路 `PidState` 对 1 kHz 控制回路没有收益，反而增加 ROS 线程/网络负载；`tune_pid.launch` 里也专门用 `topic_tools/throttle` 把它们降到 20 Hz 才能画图。

### 2.6 PID（`include/.../hero_chassis_controller.h:45-70`）

- `Pid::computeCommand(error, period)`，四个轮独立；`p=2.4, i=0.8, d=0, i_clamp=±0.8, antiwindup=true`。
- 输出 clamp ±`effort_limit`=5 Nm（与 URDF `max_effort=5` 一致）。
- 实测稳态：`vx=0.3` 时 error=0.0022 rad/s、P=0.005、I=0.072、out=0.077 Nm；`vy=0.3` 时 error=-0.007、I=-0.158；`wz=0.5` 时 error=-0.023、I=-0.272。**PID 本身工作正常，积分确实在消除稳态误差**。
- 问题在静止：目标 0 时，滤波后轮速的接触抖动（0.01~0.1 rad/s）经 P=2.4 变成 0.02~0.24 Nm 的力矩踢；`i_clamp` 足够大，若闩锁不频繁清零，积分会随机游走。实测零指令段 PID 活跃比例 2%~41%，`|out|` 平均 0.1~0.37 Nm。

### 2.7 参数逐项审计

| PID p/i/d | 2.4/0.8/0 | 稳态/上升都很好 | 不要加大 P；静止问题用门控/死区解决，不是调 PID 能解决的 |

### 3.1 启动与静置

**落地瞬态**（`main` 前 8 s）：GT z 从 0.500 落到 0.1448（-0.355 m），轮速峰值 **16.07 rad/s**（落地冲击），GT xy 只移动 (-1.5, -2.3) mm，odom xy (0.0, -3.0) mm。**落地本身不会造成大的 odom 跳变**（只有 3 mm），问题在落地后的长时间整定。

**`static_a`（8~128 s，零指令，120 s）**：

### 3.3 里程计标定与误差分解

用“GT 本体系速度 / 实测轮速”做辨识（`main` 稳态段）：

| 量 | 分段辨识 | 均值/中位 | 与配置对比 |
|---|---|---|---|
| 前向半径 `r_vx` | 0.07631~0.07643（vx_p/vx_n/5 档扫频） | **0.07636 / 0.07634** | 配置 0.07625，+0.15% → 前向几乎完美 |
| 横移半径 `r_vy` | 0.07528~0.07548（vy_p/vy_n/方形四边） | **0.07541 / 0.07541** | 配置 0.07625，**-1.1%** → 横移 odom 系统性偏大 1.1% |
| yaw 系数 `k` | wz_p=0.3866, wz_n=0.3948, 四个 1 rad/s 转弯=0.3943~0.3953 | 0.3935 / 0.3948 | 配置 0.3898；纯 +0.5 偏低，-0.5 和短转弯偏高 |
| odom/GT yaw 比 | wz_p **1.002**, wz_n **1.018**, 转弯 **1.013~1.016** | **1.013 / 1.014** | odom 平均**多报 1.3%** yaw |
| circle（边走边转） | GT wz 0.487 vs odom 0.500 | **1.027** | 复合运动滑移最大，odom 多报 2.7% |

**误差的因果链（重要）**：

1. 前向/横移的 **本体系速度与轮速基本一致**（body vy/vx ≈ 0，见 3.2），所以“横向漂移”不是轮子打滑，而是 **odom 航向（yaw）与真实航向不一致**。
2. 例：`vx_p` 时 GT 航向 -1.86°、odom 航向 -0.03°，车实际沿 **世界 -1.86°** 方向走 2.96 m，odom 沿 **世界 0°** 积分 → 世界 y 差 96 mm，而 odom 的本体系 vy=0。实测 GT 世界位移 (2964.9, -94.8) mm，与 `2.96*sin(1.86°)=96 mm` 完全吻合。
3. 扫频段 odom 航向误差已达 **-4.2°**，于是 14 m 直线后 odom 位置误差 **1.32 m**（见 3.4）。
4. 航向误差来源依次为：
   - 启动整定：-1.23°（其中 0.75° 被门控吞掉，0.48° 是滑移）；
   - 负向 0.5 rad/s 纯转：odom 多报 1.8% × 280° ≈ **+5°**（stop6 再贡献 0.8°）；
   - 短 1 rad/s 转弯：每次多报 1.4% × 74° ≈ **+1.0°**；
   - circle 复合运动：多报 2.7% × 2 圈 ≈ **+19°**；
   - circle 后静止蠕动：**-12.7°**（odom 冻结，完全不跟）。

**旋转中心偏移**：每个 1.5708 s 的 1 rad/s 转弯，GT `base_link` 平移约 **37 mm**（odom 只 0.3 mm）。按 74° 转角反算，等效旋转中心离 `base_link` 约 **31 mm**；四个转弯累计 ~15 cm 的不可观测平移。这是麦克纳姆原地转时的轮-地滑移/滚子不对称，纯轮式 odom 无法建模。

### 3.6 参数/工况 A/B

> `pidzero` / `thr1` / `spawnlow` 均为 settle 8 s + 零指令 60 s，与 `main` 的 `static_a` **前 60 s**（68.5 mm / -1.27°）直接可比。`wheel` 列为“不加门控、直接积分原始轮速”的轮式 odom。

| 会话 | 条件 | GT 60 s 漂移 | GT dyaw | odom 漂移 | wheel（无门控） | PID 活跃 | `Σabs(ω)` | 说明 |
|---|---|---|---|---|---|---|---|---|
| `main` | z=0.5，门限 0.2，正常 PID | **68.5 mm** (13.3,67.2) | **-1.27°** | 0.5 mm | 18.9 mm / -0.79° | 4% | 0.044 | PID 间歇刹车 → 车体被接触力推着滑 |
| `pidzero` | z=0.5，门限 0.2，p=i=d=0 | **23.8 mm** (1.0,23.8) | -1.94° | **65.4 mm** | **144.2 mm / -14.8°** | 19%（输出恒 0） | 0.105 | 落地没有阻尼；轮子自由滚，车体反而少滑，但 odom 大幅漂 |
| `thr1` | z=0.5，**门限 1.0**，正常 PID | **1.8 mm** (0.2,1.8) | **-0.03°** | **0.0 mm** | 41.0 mm / +4.2° | **0%** | 0.030 | 闩锁“粘住”、PID 完全不算；轮子自由空转，车体几乎不动 |
| `spawnlow` | **z=0.1466（无落地）**，门限 0.2，正常 PID | **182.0 mm** (178.3,-36.4) | +1.36° | 0.1 mm | 14.5 mm / +0.29° | 1% | 0.054 | **无落地也没有变好，反而更差**：说明落地不是主因，门限/闩锁才是 |
| `fc20` | z=0.5，门限 0.2，**fc=20 Hz** | **1.4 mm**（30 s；main 30 s 为 52.7） | +0.19° | 0.0 mm | 1.2 mm / -0.17° | **0%** | 0.013 | 低通把轮速噪声压到门限下，闩锁不再抖；**阶跃无退化** |

**这组 A/B 的结论（很重要）**：

1. **静止漂移的能量来自底盘接触/滚子，不是速度环把车“推”走**：p=i=d=0 时车体 60 s 仍漂 23.8 mm（甚至比正常 PID 的 68.5 mm 小），说明轮子上的驱动力不是来源；PID 的间歇刹车只是把“轮子滚”切换成“车体滑”。
2. **正常 PID 反而把车“刹”成了滑移**：正常 PID 在零指令段有 4% 的时间在算（闩锁抖动），每次都输出 0.1 Nm 量级的刹车力矩；轮子被反复刹住，地面接触力就把 **车体** 推着滑（68.5 mm），而轮子几乎不转（wheel 只 18.9 mm / -0.79°）。所以 odom 只记 0.5 mm，真车却动了 68.5 mm —— 这正是“静止自动偏移 + TF 不动”的机理。
3. **把 `zero_speed_threshold` 从 0.2 提到 1.0**，闩锁一次性粘住（PID 活跃 0%），车体 60 s 只漂 **1.8 mm / -0.03°**，odom 0.0 mm。代价是轮子自由空转 41 mm / 4.2°（被门控丢掉；此时车体确实没动，丢掉是对的）。
4. **但落地阶段仍然需要 PID 阻尼**：`pidzero` 的前 8 s GT 位移 (16.0, -48.3) mm、odom (0.3, -66.8) mm，而正常 PID 只有 (1.5, 2.3) / (0, -3) mm；`thr1`（正常 PID + 门限 1.0）的落地是 (2.3, -4.0) mm，同样很小。所以最佳策略是 **落地时保留 PID 阻尼，落稳后闩锁粘住直到下一条非零指令**——而不是“一直闩锁”或“一直 PID”。
5. **低通 fc=20 也能修**：`fc20` 的 30 s 静置只有 1.4 mm / +0.19°（main 同窗口 52.7 mm），六向阶跃 rise90 0.19~0.24 s、稳态误差与 main 相同，**没有可测的动态退化**。它与“门限 1.0”是同一个机理：把滤波后的轮速噪声压到门限以下，闩锁不再反复进出，PID 不再间歇刹车。两者可叠加；若只改一个且不想动门控状态机，**fc 150→20~50 Hz 是最小改动**。
6. **出生高度不是主因**：`spawnlow` 把 z 从 0.5 改到“静止高度”0.1466，落地只剩 -2 mm（前 8 s GT 只 (-4.0, 0.1) mm），但 60 s 静置仍漂 **182 mm / +1.36°**（轮速只 14.5 mm，PID 活跃 1%）——没有落地，0.2 门限照样把车“刹成滑移”。**把出生高度改低既不是必要条件，也不充分**；真正的开关是闩锁/门限。
7. 以上只是 **参数级** 的静止修复，不能修 3.3 的“运动 yaw 比例/复合滑移”；后者需要 IMU（5.2）。
8. **注意接触初值的随机性**：每次 Gazebo 启动的落地/滚子相位不同，同样参数下 60 s 漂移在 52~68 mm 间波动（spawnlow 甚至 182 mm）。但四次 A/B 的共同规律是：**静止时 PID 只要还在“算并刹车”，漂移就大（68~182 mm）；PID 完全不算（thr1/fc20）就 ~1~2 mm**。所以结论看机理与量级，不要死抠单次毫米数。

> **窗口说明**：`fc20` 用的是 `steps` 工况，静止段只有 30 s；其余 A/B 统一取 `static_a` 前 60 s。`main` 的 30 s 窗口为 52.7 mm，与 fc20 的 1.4 mm 直接可比。
>
> 若只允许改一个参数：**`zero_speed_threshold: 0.2 → 1.0`**（或 `low_pass_filter_fc: 150 → 20~50`），并建议同时把 `staticOffsetIntegralClear` 改成“进入后粘住、仅在目标非零时退出”的迟滞（见 5.3）。

|---|---|---|---|---|
| 11.0 s | 只发 **1 条** `vx=0.3` | 0→0.296 | — | — |

### 3.7 数据质量

- `/odom` 996 Hz、`/tf` 与 odom 同 stamp；odom 接收延迟均值 0.36 ms，最大 1 ms（低于 1 个控制周期）。
- `/joint_states` 195~200 Hz（配置 200）；CSV 200 Hz，无缺行。
- RTC 0.537；整个 `main` 记录 86887 行、434.4 s，无中断，`/cmd_vel` 200 Hz 持续发布。
- PID 状态在闩锁时停止更新（`age` 可到 40 s），已作为“闩锁判定”使用，不是数据丢失。

## 4. 根因分析（按影响排序）

### R1（P0）没有 `/cmd_vel` 看门狗，最后一条指令永久保持

- 代码：`doCmdVelCallback` 只写 `chassis_velocity_cmd_`；`update()` 每周期都用它，没有任何超时。
- 操作：`src/keyboard.cpp` 只在按键时 `publish` 一次，然后立刻把内部 `cmd` 清空，**不再发布 0**；`default: continue` 还跳过了 `rate.sleep()`（EOF 时 100% CPU）。
- 实测：1 条 0.3 m/s 指令 → 2.96 m / 10 s。
- 影响：把“松开按键应停车”变成“一直开/一直转”；转弯参数 6.28 rad/s 时尤其危险；用户很容易误判为“静止漂移/自动偏移”。

### R2（P0）轮式 odom 的 yaw 标定随工况变化，且无 IMU 融合

- 单一 `k_effective=0.389792` 只对“+0.5 rad/s 纯转”成立（ratio 1.002）；对 -0.5（1.018）、短 1 rad/s 转弯（1.014~1.017）、复合 circle（mode 1 1.027、mode 0 1.046）都偏。
- 物理原因是麦克纳姆轮在转向/复合运动时的纵/横向滑移，轮速与真实 yaw 的关系不是常数；纯轮式 odom **不可观测**。
- 实测后果：启动 1.8° → 扫频 4.2° → circle 后 18.5° → 最终 34.9°；位置误差被航向误差按 `L·sin(Δψ)` 放大（14 m 直线 → 1.32 m）。
- 这解释了用户说的“里程计和真实情况有很大偏差、tf 坐标变化也有偏差”；TF 与 odom 同源，所以 TF 必然同样偏。

### R3（P0，启动段）闩锁抖动 → PID 间歇刹车 → 车体被“刹成滑移”

- `zero_speed_threshold=0.2` 对静止轮速抖动（实测 `Σabs(ω)` 0.03~0.15）太紧，闩锁反复进出；零指令段 PID 活跃 4%，每次输出 0.1 Nm 量级的刹车力矩。
- 轮子被反复刹住，地面接触力转而推动车体：**60 s GT 滑移 68.5 mm，而轮式 odom 只 0.5 mm**；`p=i=d=0`（不刹车）时 GT 反而只漂 23.8 mm。
- **A/B 已证实可修**：`zero_speed_threshold=1.0` 让闩锁“粘住”，PID 活跃 0%，同一工况 60 s 只剩 **1.8 mm / -0.03°**；落地阶段的 PID 阻尼仍然保留（前 8 s GT 只 (2.3,-4.0) mm）。见 3.6。

### R4（P1，停止后）底盘接触蠕动 + odom 冻结

- `static_b`（circle 后静止 120 s）：轮速只有 0.002~0.16 的抖动，GT 却以 ~0.1°/s、1.1 mm/s 持续滑/转，120 s 累计 **177 mm / -12.7°**；原始轮速积分只有 35 mm / +0.7°，方向都不一致 → **纯滑移**。
- 这一段没有用 `thr1` 复测（`thr1` 只测了启动静置），所以“提高门限/粘住闩锁”是否也能压住它，需要额外实验；从轮速几乎为 0 看，更可能是 64 个零阻尼 roller 的接触极限环（plant），而不是 PID 力矩。
- 门控把这一段完全冻住：真车漂 12.7°，TF 一动不动。这是“静止自动偏移”最直观的来源之一，但轮式 odom 本来就看不到滑移；根治要靠 IMU（yaw）和/或给 roller 加阻尼（模型）。
- `mode0` 的 circle 后 30 s 静止也出现 **+3.50°**（3.6.1），与 mode 1 的 static_b 同性质，说明这一段与“世界系/本体系”无关。

### R5（P2，已降级）启动从 0.5 m 落地只是“激励”，不是 68.5 mm 的主因

- `hero.launch` 固定 `-z 0.5` → 落地 0.355 m、轮速峰值 16 rad/s；但正常 PID 把落地阻尼住了（前 8 s GT 只 (1.5, 2.3) mm）。
- `spawnlow`（z=0.1466，无落地）在**相同 0.2 门限**下 60 s 仍漂 **182 mm**；`thr1`（0.5 m 落地 + 门限 1.0）只有 **1.8 mm**。→ **落地高度不是主因，闩锁/门限才是**。
- 仍建议避免 0.5 m 自由落体（减少冲击/滚子损伤、缩短整定），但不要把它当作静态漂移的修复。

### R6（P1）mode 1 + 本体遥控 + 1 kHz TF 查询

- `key` 发的是本体系速度，`mode: 1` 当世界系用；车转过 90° 后按“w”会往世界 +x 走，不是车头方向。
- mode 1 用自身 odom TF 闭反馈，航向误差直接变成世界速度方向误差（实测方向误差 = -航向误差）。
- `lookupTransform(..., Time(0), 0)` 在 1 kHz RT 线程里，首周期必失败并静默回退；监听滞后时用“最新”而非本次时刻，转弯时 yaw 滞后。

### R7（P2）TF/odom 发布语义与频率

- `z=0` vs 真实 0.1448 m；`base_link` 被当成地面点。
- 1 kHz `/odom`、`/tf`、4×`PidState`；`/tf` 自环；无协方差；无 reset 服务。

### R8（P2）运动学参数单一化与低层滑移

- `r_vy` 比配置小 1.1%；低通 150 几乎不滤；加速度限幅 2 rad/s² 使 1.5708 s 的 90° 只转 74°；原地转中心偏 31 mm（37 mm/次）。
- 这些是 1%~2% 量级的残差；在 R2 的 35° 航向误差面前不是主因，但修完 R1~R6 后会显露。

## 5. 解决方案

> 以下均为建议，**本次未改任何代码/配置**。按优先级给出；每条都对应上面的实测证据。

### 5.1 P0：加 `/cmd_vel` 看门狗（改动最小、收益最大）

在控制器里记录 `last_cmd_time`，`update()` 开头：

```cpp
if ((time - last_cmd_time_).toSec() > cmd_vel_timeout_) {   // 建议 0.2~0.5 s
    chassis_velocity_cmd_ = ChassisVelocity{};              // 或只清 vx/vy/wz
}
```

- `cmd_vel_timeout` 做成参数（默认 0.3 s），可用 `dynamic_reconfigure`。
- `keyboard.cpp` 同时改成 **50 Hz 持续发布**（松开按键也发 0），并修掉 `select` EOF/`continue` 的空转；或者只保留“持续发布”这一条也能解决。
- 验证：用本次 `stale` 工况，1 条指令后应在 0.3 s 内停，而不是 2.96 m。

### 5.2 P0：yaw 用 IMU 融合（解决 R2/R3 的航向误差）

`rm_gazebo`/`rm_description` 已支持 IMU；当前 URDF 没有 IMU，仿真日志里明确说 `No imu specified`。建议：

- 给 `hero.urdf.xacro` 加 `imu`（或实车接 IMU），控制器订阅 `/imu/data` 的 `angular_velocity.z`。
- odom 的 yaw **优先用 IMU 积分**（或互补滤波：`yaw = α(yaw_odom) + (1-α)(yaw_imu)`，α≈0.02），位置仍用轮速 `vx/vy`。
- mode 1 的旋转也用同一 yaw，而不是查 TF。
- 这能同时修：
  - 启动/停止的 yaw 滑移（static_b -12.7°、stop5/6 的 3.7°）；
  - 正反/短转/复合运动的比例误差（1.002~1.027）；
  - mode 1 的“方向误差 = -航向误差”。
- 若不能加 IMU：至少 **双向 + 复合运动** 重新标定 `k`，并在报告/参数里写清适用范围；残差仍会有 1~2°/圈。

### 5.3 P0：把“静止”做成粘滞/迟滞状态（**不要**简单删掉门控）

A/B 结论：**门控本身是对的**——静止时轮子可能自由空转（`thr1` 中 41 mm / 4.2°），而车体不动；此时积分轮速反而错。问题在 **门控反复进出，PID 间歇刹车**。推荐：

```cpp
// 进入静止：目标为 0 已持续 200 ms（等减速结束） 且 Σabs(ω) < enter_thr (建议 1.0)
// 保持静止：只由目标非零或 Σabs(ω) > exit_thr (建议 1.5) 退出；进入时 reset 一次
// 静止期间：四轮命令恒 0（不要再被轮速噪声拉回 PID）；odom 冻结
```

- 参数：`zero_speed_threshold` 0.2 → **1.0**（A/B：60 s 68.5→1.8 mm，yaw -1.27→-0.03°）；**或 `low_pass_filter_fc` 150 → 20~50 Hz**（A/B：30 s 1.4 mm，阶跃无退化）；两者可叠加。建议同时加 `enter/exit` 两个门限和 100~200 ms 去抖。
- 不要在静止时“刹住”轮子：`pidzero` 证明刹住会让车体滑得更多；让轮子自由（命令 0）反而车体更稳。
- 代价：门控死区 ≈ 1.0/(4·r) ≈ 0.019 m/s；更慢的真实运动（被推）不会被积分。需要慢速精度时，用 IMU/视觉，而不是把门限降到 0.2。
- 若确实想让 odom 连续：只在“轮速方向与车体运动一致”时积分，静止滑移/空转必须靠外部传感器排除。**不建议无条件删掉门控**（会引入 thr1 的 41 mm / 4.2° 假运动）。

- 不要在每次“进入”时清 PID 后又允许它下一周期重启（当前实现会抖动）。
- 把“目标为 0”和“轮速为 0”分开：**目标为 0 就先按斜坡把轮速降到 0，再判断是否静止**，而不是 target=0 就立即闩锁。
- 静止时如果要“锁死”车，应该用 **制动/阻尼力矩**（或短时位置保持），而不是把 odom 冻住。

### 5.4 P2：启动流程（出生高度是次要项）

- A/B 已证明：**把出生高度从 0.5 改到 0.1466 不能修静止漂移**（182 mm，甚至更差）；**先做 5.3 的粘滞闩锁**。出生高度仍建议避免 0.5 m 自由落体（缩短整定、减少冲击），但它是次要项。
- 控制器加 `~reset_odom`（`std_srvs/Empty`）服务；启动/重载控制器后先 reset，再开始积分。
- 控制器重载会把 odom 从 0 开始，而车可能已在 (x,y)——**这是“很大的偏移”的另一种来源**。加服务 + 文档说明；或在 `init` 里从参数/当前 TF 初始化位姿。
- 如果保留 0.5 m 落地：unpause 后先让 PID 阻尼落地，等 `Σabs(ω)` 降到 `enter_thr` 以下再闩锁（5.3 的状态机天然做到），不要额外“等 2 s 再启用控制”。

### 5.5 P1：mode 与 TF 查询

- `key`/常规遥操作默认 `mode=0`；`mode=1` 在文档里明确“/cmd_vel 是世界/odom 系”，并提供运行时切换服务。
- mode 1 的 yaw **不要查 TF**：直接用 `odometry_.getChassisPose().yaw`（同一份数据，零延迟），或缓存一个 100 Hz 的 TF；若必须用 TF，用 `lookupTransform(..., time, 1ms)` 并对失败保持上一帧，不要静默回退到本体系。
- `ROS_WARN` 改 `ROS_WARN_THROTTLE(1.0, ...)`。

### 5.6 P2：TF/odom 语义与发布

- `/odom`、`/tf` 从 1 kHz 降到 **50~100 Hz**（控制仍 1 kHz）；用 `realtime_tools::RealtimePublisher` 或计数器分频。
- `z` 改为 **0.1447**（或发布 `odom→base_footprint` + `base_footprint→base_link`）；补 `pose.covariance`/`twist.covariance`。
- `PidState` 的 `publish_state` 只在调试开，或 `publish_rate` 降到 100 Hz。
- 给 `/odom` 增加 `reset` 服务；重载控制器时不要无条件 `resetPose()`。

### 5.7 P2：运动学/参数细化（在 R1~R6 修完后）

- 横移单独用 `r_vy=0.0754`（或 3×4 标定矩阵）：横移 odom 1.1% 偏差可消掉；前向 `r=0.07636`（当前 0.07625，差 0.15%，可不动）。
- `k` 按方向/工况标定，或直接用 IMU；不要只测 +0.5。**若不能上 IMU，本次数据支持把 `k_effective` 从 0.389792 调到 0.394~0.395**（各工况 odom/GT yaw 比中位 1.013）：这样 -0.5、1 rad/s 转弯、circle 的 yaw 误差会显著减小，代价是 +0.5 纯转从 1.002 变成 ~0.989（少报 1.1%）。这是一个“平均最优”而非“全工况最优”的折中，报告里应写清适用工况。
- `low_pass_filter_fc`：**150 → 20~50 Hz**（`fc20` A/B：30 s 静置 1.4 mm，阶跃 0.19~0.24 s 无退化）；odom 可用原始轮速，PID 用滤波。
- `chassis_angular_accel_limit`：若要开环转角准确，命令时间需补偿 `wz/α` 的斜坡；或降到 1.0~1.5 减少急停滑移（实测急停 yaw 惯性 3.7°）。
- `effort_limit` 降到 2~3 Nm 作为堵转/碰撞保护（正常 ≤0.37 Nm）。
- 原地转中心偏 31 mm：可在 odom 里加一个标定的旋转中心偏移（`x += -r_c*sin(yaw)*dψ` 等），把 37 mm/次补回来；但依赖地面，属经验修正。

### 5.8 P2：仿真模型（不改控制器时的根治）

- 64 个 roller joint `damping=0.0` 是 static_b 持续蠕动的强嫌疑；给 roller 加 **1e-4~1e-2** 阻尼，或测试时用 `roller_type=simple` 对比，可显著减少停转后的极限环。
- 这不是控制器代码，但直接影响“静止漂移”的可观测性；如果作业允许改 `rm_description`，建议做这个 A/B。

### 5.9 P3：测试/运维

## 8. 局限与说明

1. 所有结论来自 **Gazebo 仿真**；实车的轮速-地面关系、IMU 噪声、CAN 延迟会不同，R2/R3 的量级需实车复测。
2. 仿真的 `realistic` 16-roller 模型本身有停转蠕动（static_b 12.7°），这是 **plant 特性**，不是控制器能“算”出来的；本报告把它与控制器问题分开列。
3. 每个 A/B 只跑了 1 次（仿真随机性小，但接触仍有一点初值敏感）；静置漂移的绝对值会有几 mm 波动，结论看量级。
4. `main` 的 RTC=0.537，墙钟时间约为仿真时间的 1.86 倍；文中所有“秒”除特别说明外都是 **仿真时间**。
5. 未做 IMU 融合的实机/仿真验证（URDF 没有 IMU）；5.2 是建议，不是本次实测结论。
6. `/tf` 与 `/odom` 的数值一致性由同源代码和 25 s bag 校验确认；**“TF 偏差”= “odom 偏差”**，不是 TF 广播器另算了一份。
7. Gazebo 的接触初值每次不同：同一参数下 60 s 静置漂移在 52~68 mm 间波动，spawnlow 达 182 mm。A/B 的绝对毫米数不应被当作可重复的标定值；可重复的是“PID 静止刹车→滑移”的机理和“PID 不算→1~2 mm”的量级。
